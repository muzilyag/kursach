# Документация по тестированию Backend-части

В данном разделе описана архитектура тестирования, используемые технологии и сценарии, покрывающие функционал API. Проект покрыт 40 асинхронными тестами, обеспечивающими проверку бизнес-логики, маршрутизации и безопасности.

## Стек тестирования
* **Фреймворк:** `pytest`
* **Асинхронность:** `pytest-asyncio`
* **HTTP-клиент:** `httpx` (AsyncClient)
* **Взаимодействие с БД:** `SQLAlchemy` (AsyncSession)

---

## Архитектура тестов и изоляция базы данных

Для обеспечения стабильности и независимости тестов друг от друга реализована строгая изоляция на уровне базы данных (см. `tests/conftest.py`).

1. **Генерация схемы:** Перед началом сессии тестов (scope `session`) тестовая база данных (`public` схема в PostgreSQL) полностью очищается с помощью `DROP SCHEMA CASCADE` и создается заново (`Base.metadata.create_all`).
2. **Изоляция транзакций:** Для каждого теста (scope `function`) создается отдельное подключение к БД и стартует глобальная транзакция (`connection.begin()`). 
3. **Автоматический Rollback:** Все операции внутри теста (даже если эндпоинт вызывает `db.commit()`) перехватываются фикстурой. По завершении теста происходит принудительный `await trans.rollback()`. Это гарантирует, что каждый тест запускается на абсолютно чистой базе данных без риска конфликта уникальных ключей (`IntegrityError`).
4. **Фикстуры авторизации:** Настроены предсозданные мок-пользователи (`normal_user`, `admin_user`) и клиенты с уже внедренными JWT-токенами в заголовках (`auth_client_user`, `auth_client_admin`), что избавляет от необходимости дублировать логику логина в каждом тесте.

## Покрытие модулей

Все модули API протестированы на корректную обработку успешных сценариев (HTTP 200/201) и ошибок валидации, прав доступа и отсутствия ресурсов (HTTP 400, 401, 403, 404, 422).

| Модуль | Описание проверяемых сценариев |
| :--- | :--- |
| **Auth** (`test_auth.py`) | Регистрация (успешная и дубликат), логин (успешный, неверный пароль, несуществующий email), генерация `access_token`. |
| **Content** (`test_content.py`) | CRUD операции для контента. Учитывается разграничение ролей (создание/удаление только для админов). Проверка обновления прогресса просмотра для пользователей. |
| **Users** (`test_users.py`) | Получение списка пользователей, создание, обновление и удаление. Проверка ролевой модели (попытка доступа обычного пользователя к админским маршрутам возвращает `403 Forbidden`). |
| **Subscriptions** (`test_subscriptions.py`) | Просмотр тарифов, покупка подписки, превью стоимости при смене тарифа (калькуляция скидки за неиспользованные дни). Проверка обработки ошибок при несуществующих тарифах. |
| **Reports** (`test_reports.py`) | Генерация отчетов (активность, выручка, сезонность). Обработка query-параметров. Проверка возврата `404 Not Found` при попытке экспорта пустых данных в CSV/PDF. |
| **Stats** (`test_stats.py`) | Доступ к дашборду статистики. Проверка защиты роута (допуск только авторизованных пользователей с ролью `admin`). |
| **Metadata** (`test_tags.py`, `test_genres.py`, `test_copyright_holders.py`) | CRUD операции над тегами, жанрами и правообладателями. Проверка возвращаемых структур данных (схем Pydantic). |
| **Error Handlers** (`test_error_handlers.py`) | Обработка системных ошибок FastAPI: `404 Not Found` (неверный URL) и `405 Method Not Allowed` (неверный HTTP-метод). |

## Как запустить тесты

Убедитесь, что ваше виртуальное окружение активировано, а в файле конфигурации (`.env` или `settings`) указан `TEST_DATABASE_URL` для тестовой БД.

**1. Запуск всех тестов:**
```bash
pytest
```
**2. Запуск с подробным выводом (verbose):**
```bash
pytest -vv
```
**3. Запуск конкретного тестового файла:**
```bash
pytest tests/test_auth.py -vv
```
**4. Запуск конкретного теста (по имени):**
```bash
pytest -k "test_buy_subscription" -vv
```
